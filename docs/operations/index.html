Operations

Audit privacy#

Audit rows (requests) store scores, the decision, and a SHA-256 and the length of the request body and of a buffered upstream response. They store no prompt or response content unless content storage is enabled, either for every organization with AUDIT_STORE_CONTENT=true on the gateway, or for one organization with PATCH /v1/organizations/{id} and {"audit_store_content": true} (admin role). Streamed responses are not buffered, so their response columns stay empty.

Each request gets one audit row. action is allow, block, error (the upstream failed or the client left before it answered) or output_leak (the canary showed up in the answer).

Upstream behaviour#

UPSTREAM_LLM_TIMEOUT (default 5m) is the longest wait for the first byte and for any later silence; a long stream is not cut off while data flows. If the client hangs up before the upstream answers, the upstream request is cancelled at once. A client that only half-closes its side (shutdown(SHUT_WR)) sends the same FIN as one that left, and the gateway cannot tell them apart without writing to the connection, so by default it cancels too. Set CLIENT_HALF_CLOSE=wait to serve such clients: the gateway then cancels only on a connection reset and otherwise relies on the timeout.

Output guard#

The gateway checks the model's answer before the client sees it. It rewrites choices[].message.content (and choices[].text for legacy completions) in whole responses. In streams it keeps a 256-character window per choice, so a pattern split across chunks is still caught, and rebuilds each chunk with its id, model and other fields unchanged. A stream therefore runs about 256 characters behind the upstream. Held text is flushed at finish_reason and at [DONE]. An upstream body that is not JSON cannot be checked and gives 502.

  • Images and links. Markdown images, HTML <img> tags and reference definitions whose host is not on the allowlist are removed ([REDACTED:image]). Links to other hosts keep their text and lose the URL. Bare image URLs that carry a query string are replaced with [REDACTED:url]. With the default empty allowlist every image and link is removed. An <img> tag is kept only if every src and srcset URL is on the allowlist.
  • Personal data. Each match is replaced with [REDACTED:<type>]: email, phone (Vietnamese numbers in the +84, 84 and 0 forms, mobile and landline), cccd (12 digits starting with 0), card (13 to 19 digits that pass the Luhn check) and, when enabled, ipv4.
  • Canary. When enabled, the gateway puts a random token for each request in the system prompt (appended to a leading system message, or as a new one; legacy completions get none). If the model repeats it, the response is refused with 400 content_filter (in a stream, an error event that ends it), or the token is redacted. Either way the row's action is output_leak.
  • Reasoning. The reasoning and reasoning_content fields that Ollama and vLLM send are guarded like the answer, or dropped.
  • Refusals and tool calls. refusal is guarded like the answer. Tool-call arguments (tool_calls[].function.arguments, and the older function_call) are parsed as JSON and each string is guarded on its own, so they stay valid JSON. In a stream, each call's arguments are held whole and sent when its choice finishes. A canary in tool-call arguments refuses the response even in redact mode.
  • Content parts. Text parts are guarded. A part that is not text cannot be checked: a whole response gets 502, and a stream ends with an error event.

The audit row counts what was removed per type in pii_entities, as output:email=2. It never stores the content. These settings apply to every organization; there are no per-org output settings yet.

Indirect injection and tool poisoning#

Text that reaches the model from a third party (tool results, retrieved documents, and the tool descriptions an MCP server supplies) is untrusted. The gateway scores it apart from the user's own text.

Part Name in SCAN_ROLES Default Notes
user messages, legacy prompt and suffix user on classified together
tool (and function) messages tool on each message classified on its own
tools[].function.description and every description in parameters (also legacy functions[]) tool_descriptions on detector plus the MCP poisoning signals
system messages system off classified with the user text, never rewritten
assistant tool_calls[].function.arguments from history tool_calls off the string values of the JSON arguments, never rewritten

User and tool text is sanitized whether or not it is classified. A key that differs from tools or functions only in case is refused with 400. While tool_descriptions is on, so is a tools field that is not a list, a name or description that is not a string, and a schema nested deeper than 32 levels.

Scoring. Each tool result and each tool definition gets its own score. An instruction found in a tool result is indirect_injection; anything flagged in a tool description is tool_poisoning. A tool description's score is the larger of the detector's and the MCP signals': a secret path (~/.ssh, id_rsa, /etc/shadow), <IMPORTANT>, "do not mention this to the user", "send all emails to" or invisible characters reach 0.9 on their own; weaker signals ("Before using this tool", mcp.json, a description over 1500 bytes, ...) count 0.5 each and only block together. The request is blocked when the largest untrusted score reaches INDIRECT_BLOCK_THRESHOLD. The audit row's injection_score and injection_label hold the strongest finding, direct or not. Untrusted text is limited to 128 KiB per request (413 above).

Spotlighting applies to tool results only:

SPOTLIGHT Effect on tool results
off (default) forwarded as sanitized, without markers
delimit wrapped in <<untrusted-XXXX>> ... <</untrusted-XXXX>> with a random boundary per request, and a note in the system message telling the model that text inside is data
datamark every space and tab replaced by ˆ (U+02C6), with a system note explaining the marker

The sanitizer strips spoofed markers from client text and raises the anomaly score when it finds one, so a tool result cannot close the block it sits in. An org can override scan_roles and spotlight through PUT /v1/organizations/:orgId/guard-settings; the gateway reads them on every request and fails closed with 503 if it cannot.

POST /guardrail/scan takes text, documents (at most 64, 128 KiB in total; source is web, email, file, tool or other), or both. The response has injection_score, injection_label, anomaly_score, had_tag_chars, had_bidi, bytes_removed, sanitized_text, blocked, verdict and a documents[] entry per document with its own score, category, detector_category, rules, blocked and verdict. A document is blocked at INDIRECT_BLOCK_THRESHOLD or when its anomaly score reaches 0.6. (toxicity_score is still in the response for compatibility and is always 0.)

POST /guardrail/scan/tools checks each tool's description and every description nested in inputSchema (at most 256 tools). Each tool gets score, category, signals, blocked, verdict and fields (the descriptions that scored at least 0.3 or carried a signal, by path).

go run ./cmd/eval -path tool scores the eval set through this untrusted-content path.

Per-organization exemplars#

/v1/organizations/:orgId/exemplars stores {"label": "block"|"allow", "text": "...", "source": "..."} (at most 1,000 per org, 4,000 characters each). A block text counts as an attack for that org's requests (injection.category tenant_exemplar), and its calibrated L3 score is a floor for the fused score; an allow text lowers L3 only. The gateway embeds each org's exemplars once and reloads them when they change (checked at most every 5 s). They need the L3 model. Tenant exemplars live in the database only, never in this repository.

Metrics#

Both services serve Prometheus metrics at /metrics on a listener of their own (METRICS_ADDR), so the endpoint is not reachable through the API port. Keep that port on the internal network.

Gateway metric (prefix guardspec_gateway_) Labels
requests_total, request_duration_seconds route, status, decision (allow, route, block, error, output_leak; none before the guard ran)
route_selections_total source (rule, project, org, env, stub), outcome (ok, failed); the upstream's name is not a label
detector_duration_seconds, detector_errors_total layer (l1, l2, l3), per chunk
upstream_duration_seconds path, outcome (ok, error)
upstream_errors_total path, code
policy_eval_errors_total stage (load, eval, route)
output_guard_actions_total kind (image, link, url, canary, email, phone, cccd, card, ipv4)
ratelimit_rejections_total limit (requests, tokens)
tenant_requests_total (with METRICS_TENANT_LABELS=true) org_id, decision

The control plane exports guardspec_control_plane_requests_total, guardspec_control_plane_request_duration_seconds, guardspec_audit_retention_runs_total{result} and guardspec_audit_retention_deleted_rows_total. Labels take values from fixed sets only; API key IDs are never a label.

Tracing#

OpenTelemetry tracing is off unless OTEL_EXPORTER_OTLP_ENDPOINT (or OTEL_EXPORTER_OTLP_TRACES_ENDPOINT) is set. Spans go over OTLP/HTTP; gRPC is not supported. The gateway continues a W3C traceparent from the client and creates a server span per request with children sanitize, detect, policy, upstream, output_guard and output_guard.stream. OTEL_PROPAGATE_UPSTREAM=true sends traceparent to the upstream; it is off by default because it tells the upstream the trace ID.

Rate limits#

Each API key gets two token buckets: requests per minute and, optionally, tokens per minute (estimated as body bytes / 4). A key's own rpm_limit and tpm_limit win; keys without one get RATE_LIMIT_RPM / RATE_LIMIT_TPM. Over the limit: 429 with Retry-After and {"error":{"message":"...","type":"requests","code":"rate_limit_exceeded"}} (type is tokens for the token limit); no audit row. Buckets are kept in memory per gateway replica, and a key's limits are cached for 30 seconds.

POST  /v1/organizations/{id}/api-keys           {"alias":"bot","rpm_limit":600,"tpm_limit":200000}
PATCH /v1/organizations/{id}/api-keys/{prefix}  {"rpm_limit":null}   # back to RATE_LIMIT_RPM

Users, invites and projects#

Admins invite people with POST /v1/orgs/{id}/invites {"email":"a@example.com","role":"member","ttl_hours":72}. No e-mail is sent: the response carries a one-time gsinv_... token that the admin passes on, and POST /v1/invites/accept {"token":"...","password":"...","display_name":"A"} creates the user (or adds the membership to an existing account whose password matches). Only the token's SHA-256 is stored. Nobody can invite with a role above their own.

A project groups API keys inside an organization. A key or a policy created with a project_id belongs to that project; the gateway evaluates the project's policies first, then the org-wide ones.

Identity, SSO and two-factor authentication#

Sessions. A login creates a row in sessions; the token (12 hours) carries its id as sid. Logout, DELETE /v1/auth/sessions/:id, a password change (other sessions), disabling a user and an admin's revoke-sessions end sessions at once on the replica that made the change and within 15 seconds on the others. Tokens issued before migration 013 have no sid and are refused: everyone logs in again after the upgrade.

Two-factor authentication (TOTP, RFC 6238: SHA-1, 6 digits, 30 s, one step of skew). POST /v1/auth/mfa/totp/setup returns the secret and an otpauth:// URL (the UI draws the QR code itself); .../confirm {code} turns it on and returns 10 recovery codes, shown once and stored as bcrypt hashes. Enrollment is trust on first use: whoever completes it at the first login after an org requires 2FA (the account's password holder) chooses the authenticator. A login of a user with 2FA returns {"mfa_required": true, "mfa_token", "methods": ["totp","recovery"]}; POST /v1/auth/mfa/verify {mfa_token, code} finishes it. The mfa_token is a 5-minute JWT allowing 5 attempts and one success; a TOTP code is refused for the step it was used in (and earlier ones), a recovery code works once. Ten wrong codes in a row lock the user's second factor for 15 minutes (doubling every 5 more, at most 24 hours; 429 mfa_locked, logged as mfa.locked), whatever the token or address. The secret is encrypted with MFA_ENC_KEY (AES-256-GCM, bound to the user id). Back the key up with the database: without it no user with 2FA can log in.

A member's 2FA reset and session revocation act on the user everywhere, so they need an instance administrator or an owner of every organization the user belongs to (403 not_sole_authority otherwise).

Org security (PUT /v1/organizations/:orgId/security, owner): require_mfa makes members without 2FA enroll at their next login ({"mfa_enroll_required": true, "mfa_token"}; that token can only call the 2FA setup endpoints) and refuses existing sessions without 2FA (403 mfa_required); sso_satisfies_mfa lets SSO sessions pass; allowed_login_methods (password, google, oidc:<provider id>; unset allows all) refuses sessions of other methods (403 login_method_not_allowed); session_lifetime_hours (1-12) shortens sessions for this org; domain_join adds SSO users of a verified email domain on first login, with a role up to admin. A domain can be joined only if the instance administrator listed it in the provider's allowed_domains.

SSO (OpenID Connect, Google as a preset). An instance administrator (users.is_instance_admin; the bootstrap admin, which is the earliest owner of the default org at migration 013) adds providers at /v1/admin/identity-providers {"type":"google","client_id":"...","client_secret_env":"OIDC_SECRET_GOOGLE","allowed_domains":["example.com"],"auto_provision":true}. Register <PUBLIC_BASE_URL>/v1/auth/oidc/<id>/callback as the redirect URI. The flow uses PKCE (S256), state and nonce (stored server-side for 10 minutes); the state is also bound to the browser by an HttpOnly, SameSite=Lax cookie set at start (login CSRF), so the UI navigates to .../start rather than fetching it. The callback verifies the ID token through the provider's JWKS and requires email_verified; Google logins with allowed_domains must also carry a matching hd claim. The callback redirects to /ui/#/auth/callback?code=<60 s one-time code> (or ?error=<code>), which POST /v1/auth/oidc/exchange turns into the same answer as a password login, so 2FA still applies. Identities match on (provider, subject). A new identity whose email matches an existing account links to it only when the provider has trust_email_for_linking (off by default) and the account has no password and no identity; otherwise the login is refused with account_exists, and the owner of the account links the identity from their profile: POST /v1/auth/identities/:providerId/link/start returns the provider's URL, the callback sends the browser to /ui/#/account?link_code=<60 s code>, and POST /v1/auth/identities/link/complete {code} with the same user's token binds it (a code is refused for anyone else, so a link URL sent to a victim links nothing). A manual link never runs domain_join. New users are created only with auto_provision and an allowed domain. Emails are stored lower-cased.

Activity log. Member, invite, API key, policy, upstream, security and config changes and 2FA resets are recorded per org (GET /v1/organizations/:orgId/activity); SSO provider and instance user changes, logins (success and failure) and the user's own 2FA events at GET /v1/admin/activity. Details never hold secrets; a failed login keeps the email masked (a***@example.com).

Bootstrap. ADMIN_EMAIL/ADMIN_PASSWORD create the first owner and instance administrator once. A later start does nothing if an instance administrator exists or the bootstrap ran before, so a deleted bootstrap admin stays deleted.

Audit retention#

The control plane deletes audit rows older than AUDIT_RETENTION_DAYS in batches, at start and then every AUDIT_RETENTION_INTERVAL. Every replica runs the job; a Postgres advisory lock lets one of them work at a time.

Kubernetes#

A minimal chart is in deploy/helm/guard-spec. It deploys the gateway and the control plane against an external Postgres; Postgres is not bundled, and the chart does not run the migrations.

kubectl create secret generic guard-spec-secrets \
  --from-literal=POSTGRES_PASSWORD=... --from-literal=GUARDSPEC_APP_PASSWORD=... \
  --from-literal=JWT_SECRET=... --from-literal=ADMIN_PASSWORD=... \
  --from-literal=MFA_ENC_KEY="$(openssl rand -base64 32)"   # back it up with the database
# migrate first, as the owner role: migrate -path migrations -database "postgres://ps:...@host/guardspec" up
helm install gs deploy/helm/guard-spec \
  --set externalDatabase.url='postgres://guardspec_app@db.example:5432/guardspec?sslmode=require' \
  --set externalDatabase.host=db.example --set dbRoles.enabled=true \
  --set controlPlane.adminEmail=admin@example.com
  • Secrets come from existingSecret. GUARDSPEC_APP_PASSWORD reaches both services as PGPASSWORD, so URLs carry no password. POSTGRES_PASSWORD is used only by the optional dbRoles hook job. MFA_ENC_KEY (see Configuration) is optional in that Secret; it can come from controlPlane.extraEnvFrom instead.
  • Metrics are served on separate ClusterIP Services (*-metrics), so exposing an API Service never exposes /metrics. serviceMonitor.enabled=true adds a Prometheus Operator ServiceMonitor.
  • Models come from a PVC mounted read-only at /models in the gateway (models.existingClaim, or the chart's own with models.persistence.enabled=true, the default). The release gateway image is built with -tags onnx and runs L1 + L2 + L3 when the models are there; with an empty PVC it runs L1 only. With models.persistence.enabled=false and no existingClaim nothing is mounted at /models: use that with gateway.image.repository=ghcr.io/guard-spec/guard-spec-gateway-full, which has the models inside. The readiness probe uses /readyz, which lists the active layers and answers 503 only when a layer the configuration requires (DETECTOR_REQUIRE_ML=true) is missing.
  • Resources: the gateway defaults (request 500m CPU / 1Gi, limit 2Gi) fit L1 + L2 + L3, which use about 900 MiB right after start.
  • Security: pods run as non-root with a read-only root filesystem, no capabilities and the RuntimeDefault seccomp profile. The dbRoles job runs as UID 70 (the postgres image's user) unless dbRoles.podSecurityContext sets one; on OpenShift it lets the SCC pick the UID.
  • Rate limits are per replica, so gateway.replicaCount multiplies the effective limit.
