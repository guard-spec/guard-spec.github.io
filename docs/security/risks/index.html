Risks and hardening

Tiếng Việt: security-risks.vi.md.

This page is for the people who deploy and operate Guard Spec. It lists the risks that remain when Guard Spec is in front of your LLM, and what you can do about each. For what the gateway does and does not protect against, read Security model and limitations first. To report a vulnerability, follow SECURITY.md.

Guard Spec is one layer of defence. It lowers the chance that an injected instruction reaches the model and limits what the answer can leak. It does not make an LLM application safe on its own.

Detection risks#

D1. An attack is not detected#

Detection is probabilistic. New phrasings, languages other than English and Vietnamese, encodings that L1 only partly decodes (such as base64) and multi-turn attacks that look harmless in each single message can pass. With the default model layers the eval set shows a true positive rate of about 0.93 at the block threshold (see Benchmarks); the rest reach the model.

What to do:

  • Design your application as if some injections reach the model: give tools the least privilege they need and ask a person to confirm risky actions.
  • Keep the output guard on; it limits what a successful injection can leak.
  • Add attacks you see in your traffic as block exemplars for your organization (Per-organization exemplars).
  • Report bypasses privately (SECURITY.md); they are in scope.

D2. A benign request is blocked#

With L2 and L3, about 1.4% of benign eval prompts are blocked, 3.5% of benign Vietnamese teencode and 1.7% of English. The Vietnamese eval and training data is synthetic, so your rate can differ.

What to do:

  • Run in front of a copy of your traffic first and read the block audit rows.
  • Add allow exemplars for false positives you see.
  • If a false block costs more than a missed attack for you, run DETECTOR_LAYERS=l1 (about 0.1% false positives, lower recall).

D3. Model layers silently missing#

When the models are missing or fail to load, the gateway logs a warning and keeps running with L1 only. /readyz then shows "degraded":true.

What to do:

  • Set DETECTOR_REQUIRE_ML=true so the gateway refuses to start without the model layers, or use the gateway-full image, which ships them.
  • Alert on degraded in /readyz and on guardspec_gateway_detector_errors_total.

D4. Indirect injection in content you do not scan#

By default the gateway classifies user messages, tool results and MCP tool descriptions (SCAN_ROLES=user,tool,tool_descriptions). System prompts and the model's tool-call arguments are not classified unless you add them, and images, audio and other non-text parts are not inspected.

What to do:

  • If your system prompt contains user-controlled or retrieved text, add system to SCAN_ROLES or turn it on per organization (scan_roles).
  • Send retrieved documents through /guardrail/scan with documents[] before you put them in a prompt.
  • Turn on SPOTLIGHT (delimit or datamark) so the model can tell data from instructions.

Application and agent risks#

A1. The agent misuses a tool#

The gateway sees tool-call arguments and guards their strings, but it does not execute or authorise tool calls and has no egress control. If the model is convinced to call a tool, the tool runs.

What to do:

  • Authorise every tool call in your application against the end user's permissions, not the model's request.
  • Restrict network egress from the services that run tools.
  • Require confirmation for actions that send data out, spend money or delete.

A2. Exfiltration through links the guard keeps#

The output guard removes images and links to hosts outside the allowlist, but keeps links to allowlisted hosts and plain-text URLs without a query string. If your UI turns bare URLs into links, it can still be used to leak data.

What to do:

  • Keep the link allowlist short; do not allow hosts where anyone can publish.
  • Do not auto-link URLs in model output, and do not load remote images in it.

Deployment risks#

P1. Services exposed without TLS#

The gateway and the control plane serve plain HTTP. API keys, session cookies and prompts cross the network in clear text unless something in front terminates TLS.

What to do:

  • Put a reverse proxy or load balancer with TLS in front of both services.
  • Use sslmode=require or stronger in database URLs.
  • Set PUBLIC_BASE_URL to the https:// origin of the control plane.

P2. Control plane or metrics reachable from the internet#

The control plane holds the admin UI and API. /metrics is served on its own listener (METRICS_ADDR).

What to do:

  • Expose only the gateway to your applications. Keep the control plane on a private network, behind a VPN or an identity-aware proxy.
  • Never route the metrics port through an ingress or public load balancer.
  • Leave ALLOWED_ORIGINS empty unless another origin really needs the API.

P3. Org upstreams point at internal hosts or receive your keys#

An org admin chooses where its named upstreams point.

What to do:

  • Keep UPSTREAM_ALLOW_PRIVATE=false (the default) unless every org admin is trusted. Cloud metadata addresses are always refused.
  • Keep UPSTREAM_KEY_ORGS narrow: it decides which org may use which UPSTREAM_KEY_* variable. The compose file sets both for a single-team setup; change them before letting untrusted users create organizations.

P4. Rate limits bypassed by volume#

Rate limits are kept in memory per gateway replica, so the effective limit grows with the number of replicas, and they do not stop a flood of connections.

What to do: put a WAF or a shared rate limiter in front of the gateway, and set provider-side spending limits.

Identity and access risks#

I1. Weak or leaked secrets#

POSTGRES_PASSWORD, GUARDSPEC_APP_PASSWORD, JWT_SECRET, MFA_ENC_KEY and ADMIN_PASSWORD protect everything. Outside GUARD_ENV=dev the services refuse missing, default or short secrets, but they cannot tell whether a secret has leaked.

What to do:

  • Generate secrets randomly (scripts/quickstart.sh does) and keep them in a secret manager, not in Git or in Helm values.
  • Never run production with GUARD_ENV=dev.
  • Rotate JWT_SECRET (signs everyone out) and the database passwords if you suspect a leak. Revoke API keys you no longer use.

I2. Lost MFA_ENC_KEY#

TOTP secrets are encrypted with MFA_ENC_KEY. Without the key, nobody's 2FA works, and the control plane refuses to start while users have 2FA.

What to do: back the key up together with the database, in a different place from the database backup itself.

I3. Any user can create an organization#

Any signed-in user can create an organization and becomes its admin. See P3 for what that admin can configure.

What to do: if your control plane is reachable by people you do not trust, use SSO with allowed_domains and keep the P3 settings strict.

I4. 2FA enrolment is trust on first use#

When an organization starts requiring 2FA, a member without it enrols at the next login with only a password. Someone who already has that password can enrol their own authenticator first.

What to do: require 2FA from the start, and reset a member's 2FA if in doubt.

I5. Wrong TRUSTED_PROXIES#

TRUSTED_PROXIES decides whose X-Forwarded-For is believed. Too broad a value lets clients choose the address used for rate limits, sessions and the activity log; an empty value behind a proxy makes every client look the same.

What to do: list exactly the addresses or CIDRs of your proxies.

Data and privacy risks#

R1. Prompt content stored in audit rows#

By default audit rows keep scores, the decision, and a SHA-256 and length of the body, not the content. AUDIT_STORE_CONTENT=true, or the per-org audit_store_content setting, stores prompts and buffered answers.

What to do:

  • Keep content storage off unless you need it, and tell your users if you turn it on.
  • Set AUDIT_RETENTION_DAYS, encrypt the database at rest and limit who can read it.

R2. Personal data passes the redactor#

The output guard redacts e-mail addresses, Vietnamese phone, ID and card numbers and IPv4 addresses with patterns. Other formats, other countries and personal data written in words are not caught. Prompts going to the upstream are not redacted.

What to do: if you must not send personal data to the LLM provider, remove it in your application before the request, or use a provider and contract that allow it.

R3. Trace IDs or metric labels leak tenant data#

Metric labels use fixed value sets, per-tenant labels are off (METRICS_TENANT_LABELS=false) and traceparent is not sent upstream (OTEL_PROPAGATE_UPSTREAM=false). Turning these on shares more with your monitoring system or the provider.

What to do: change these defaults only when the receiving system is trusted.

Supply chain risks#

S1. Tampered image, binary or model#

What to do:

  • Verify images and archives with cosign before you deploy them (Verifying releases), and deploy by digest rather than by tag.
  • Download models with models pull, which checks the SHA-256 pinned in models/manifest.yaml. In air-gapped installs, mirror only verified files.

S2. Known vulnerabilities in dependencies#

The project is pre-1.0; security fixes land in the next release only.

What to do: follow the repository's releases and security advisories, upgrade to the latest 0.x, and scan the images you run.

Operational risks#

O1. Database or admin access misused#

Anyone with database or instance-admin access can change policies, read audit rows and create API keys.

What to do: give the application role (guardspec_app) to the services only, keep the owner role for migrations, give people the lowest role they need, and review the activity log.

O2. Fail-closed causes an outage#

If policies, org settings or the detector cannot run, the gateway refuses the request (503) instead of passing it through. A database outage therefore stops LLM traffic.

What to do: run more than one gateway replica, use a highly available Postgres, and alert on 503 rates and /readyz.

Hardening checklist#

  • TLS in front of both services; database connections with sslmode=require or stronger
  • Only the gateway is reachable by applications; the control plane and metrics ports are private
  • GUARD_ENV is not dev; all secrets are random and kept in a secret manager
  • MFA_ENC_KEY is backed up separately from the database backup
  • DETECTOR_REQUIRE_ML=true or the gateway-full image; alerts on degraded
  • UPSTREAM_ALLOW_PRIVATE=false and a narrow UPSTREAM_KEY_ORGS
  • TRUSTED_PROXIES lists exactly your proxies
  • SCAN_ROLES covers every place untrusted text enters your prompts
  • A short link allowlist; no auto-linking of model output in your UI
  • Content storage off; AUDIT_RETENTION_DAYS set
  • SSO or required 2FA for everyone with admin access
  • A WAF or shared rate limiter in front of the gateway; provider spending limits
  • Images and archives verified with cosign; deployed by digest
  • Tools authorised in your application; risky actions confirmed by a person
