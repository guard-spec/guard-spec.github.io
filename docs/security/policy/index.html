Reporting a vulnerability

Guard Spec is a security component: it sits in front of LLMs and decides what reaches them. We treat bypasses of its guardrails as vulnerabilities, not only classic memory-safety or authentication bugs.

Reporting a vulnerability#

Please do not open a public issue, discussion or pull request for a security problem.

Report it privately through GitHub Security Advisories:

  1. Go to the repository's Security tab.
  2. Click Report a vulnerability (direct link: https://github.com/guard-spec/guard-spec/security/advisories/new).
  3. Describe the issue, the affected version or commit, and how to reproduce it. A minimal request body or proof of concept helps most.

If you cannot use GitHub, email security@guardspec.io with the same details. Please do not put details in a public issue.

What we consider in scope#

  • Bypassing the sanitizer, classifier thresholds or policy engine so that text the gateway should block or clean reaches the upstream model.
  • Cross-tenant access: reading or changing another organization's data, including through row-level security gaps.
  • Authentication or authorization flaws in the control plane or gateway (API keys, JWTs, roles).
  • Leaks of prompts, responses, API keys or other secrets, including through logs or audit rows.
  • Insecure defaults that survive outside development mode (GUARD_ENV=dev).
  • Vulnerabilities in our container images or release artifacts.

Out of scope: findings that require GUARD_ENV=dev or the development compose override, model accuracy without a concrete bypass, denial of service by volume alone, and issues in upstream LLMs.

Hardening#

For the risks that remain when you run Guard Spec and how to reduce them, see docs/security-risks.md.

For a security review of a deployment (architecture, data flow, what is stored where and for how long, secrets and encryption), see docs/security/.

Supported versions#

The project is pre-1.0. Security fixes land on main and in the next release.

Version Supported
main Yes
latest 0.x Yes
older 0.x No, please upgrade

After 1.0 the latest minor release and the one before it will receive fixes.

Response targets#

These are targets, not guarantees, for a small volunteer team:

Step Target
Acknowledge the report 3 business days
Initial assessment and severity 7 days
Fix for critical or high severity 30 days
Fix for medium or low severity 90 days
Public advisory when the fix is released

We will keep you informed while we work on it, credit you in the advisory unless you prefer otherwise, and request a CVE where it applies. Please give us the time above before disclosing publicly; we will agree a date with you if a fix needs longer.

Verifying releases#

docs/security/verifying-releases.md has the full procedure (signatures pinned to the release tag, SBOMs, SLSA provenance) with its output for v0.1.0. In short:

Release container images are signed with cosign (keyless, through GitHub Actions OIDC) and come with an SPDX SBOM and SLSA provenance (BuildKit attestations; docker buildx imagetools inspect <image> --format '{{json .SBOM}}'). The gateway and gateway-full images are built by .github/workflows/release.yml, the control-plane image by GoReleaser; all are verified the same way (replace guard-spec-gateway with guard-spec-gateway-full or guard-spec-control-plane):

cosign verify ghcr.io/guard-spec/guard-spec-gateway:<version> \
  --certificate-identity-regexp '^https://github.com/guard-spec/guard-spec/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Archives are covered by checksums.txt (GoReleaser, L1-only binaries) and checksums-onnx.txt (the linux _onnx tarballs), each signed with a cosign bundle next to it:

cosign verify-blob checksums-onnx.txt --bundle checksums-onnx.txt.sigstore.json \
  --certificate-identity-regexp '^https://github.com/guard-spec/guard-spec/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --ignore-missing -c checksums-onnx.txt
